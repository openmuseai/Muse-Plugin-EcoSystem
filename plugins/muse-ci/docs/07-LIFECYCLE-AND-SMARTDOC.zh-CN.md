# Muse-CI：版本、需求与 SmartDoc 流程规范

日期：2026-11-19。此文替代旧画布文档中“所有节点平铺、跨阶段自由连线、Markdown 作为新流程主要文档”的约定。历史流程及其执行语义保留，不改写既有结果。

## 产品对象与边界

版本是交付范围和发布批次；需求是可独立说明、设计、实现、测试并合并的子交付。两者是独立、持久、可授权和可查询的流程，不能只用画布上的视觉分组代替。版本引用需求的身份和交付修订，不复制需求研发节点到主画布。

层级：版本 → 需求子流程 → Step → 节点 → 文档修订 / Attempt / 产物。独立需求也可单独创建。Host 继续只承载通用 MCP Apps、会话和鉴权，CI 业务留在插件及后端。

## 版本生命周期

| Step | 节点及关键交付 | 进入下一 Step 的要求 |
| --- | --- | --- |
| 01 版本定义 | 版本目标、功能边界、粗粒度 PRD、平台/渠道、非目标、验收和风险 | 节点完成或留痕标过；对应 SmartDoc 当前修订已发布 |
| 02 版本视觉与 UI | 视觉方向、主要页面和交互、跨端约束、设计源稿位置 | 版本设计文档已发布且节点完成 |
| 03 需求拆分与交付 | 需求拆分计划；多个独立需求入口 | 所有子需求具备交付文档、真实测试报告与 MR 合并回执 |
| 04 版本回归测试 | 版本回归用例；执行报告 | 用例明确、当前输入上的测试真实执行；人工标过不能代替测试报告 |
| 05 版本上架 | 候选包、签名、版本/构建号、隐私版权与渠道材料；真实平台回执 | 实际渠道上传/提审/审核/发布分别核验，未接入平台时保持待接入 |

版本回归 Run 固定各子需求的修订。执行前后检查子需求版本；子需求发生变化不能继续将旧回归结果用于后续发布。

## 需求生命周期

| Step | 必须细化的内容 | 关键交付 |
| --- | --- | --- |
| 01 功能需求 PRD | 用户/场景/目标、范围及非目标、逐路径规则、字段、权限、异常/边界/并发/离线、平台差异、兼容/迁移、隐私和逐项验收条件 | 详细 PRD SmartDoc |
| 02 视觉与 UI | 页面/组件、视觉源稿、主路径、空态/加载/失败/禁用/恢复、Desktop/Web/Mobile 适配、可访问性 | UI 与交互 SmartDoc、源稿/截图子文档 |
| 03 方案设计与研发 | 模块、数据、协议、权限、失败恢复、并发、迁移、实施任务、风险、回滚及需求-改动映射 | 方案 SmartDoc、实现证据与来源提交 |
| 04 需求测试 | 用例 ID、关联验收项、环境、前置数据、步骤、预期、优先级；实际结果与缺陷 | 测试用例 SmartDoc、真实测试报告及不可变原始产物 |
| 05 MR 提审与合并 | 仓库、源/目标分支、MR、评审修订、平台状态、源 SHA 和合并 SHA | MR 评审记录 SmartDoc、平台回执和合并记录 |

MR 的真实状态只读核对支持 GitHub/GitLab。后端先授权受信仓库、源分支和目标分支，令牌不进入 UI。此功能不自动创建、提交评审、推送或合并真实代码。未连接仓库或未取得真实合并 SHA 时不会标记“已合并”。接口依据 [GitHub Pull requests API](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request) 与 [GitLab Merge requests API](https://docs.gitlab.com/api/merge_requests/#retrieve-information-about-a-merge-request)。

## 画布与交互

- 一个竖列是一个 Step；横向按编号表达交付顺序，仅 Step 之间显示顺序箭头。
- 仅在同 Step 内显示节点依赖。跨 Step 不画节点连线，新生命周期拒绝保存跨 Step 节点边。历史边保留执行语义但不绘制跨 Step 连线。
- 同 Step 内 A→B 按从上到下排列；无依赖且材料就绪的节点可并行。节点位置不制造隐式依赖。
- 节点仍能添加、配置 Skill/工具/SmartDoc 材料、重跑、查看历史和产物。关键交付节点保留在所属 Step；可增加其他节点和 Step。
- 主流程“需求拆分与交付”只放子需求入口及交付摘要。点击进入独立需求画布；顶部返回版本主流程，URL 与选中流程保持一致。
- 未发布材料、前序 Step 未完成、未配置执行工具、子需求未交付和缺少外部回执分别提示，不能将“不就绪”只表现为调用失败。
- Mobile 使用同一流程定义的 Step 分组列表，保留文档、配置、标过和子流程入口，不要求操作大幅横向画布。

## 人工标过

按钮文案按产品要求保留“标过”。状态为 `marked`，独立于 `succeeded`。记录操作者、原因、时间、配置修订和原状态；不新增成功 Attempt、不生成虚构产物。可撤回；撤回、上游材料和配置变化会使受影响结果过期。

普通依赖可接受留痕标过，但必需交付文档仍须发布。测试报告必须有实际执行与退出结果，MR 合并必须有平台回执，版本上架必须有渠道事实。不能通过标过这些节点或在文档写“成功”伪造验证。

## SmartDoc、总文档与材料归档

所有新流程的主要文档使用真实 `muse.smart-document/phase1` 原生格式。后端直接调用当前 SmartDocument WASM 引擎，持久保存 Yrs `docState`，下载 `.sydoc` 与现有原生插件的 profile/objectId/docState 合同一致；不是将 Markdown 或普通 JSON 改扩展名。

每个流程自动创建唯一总文档及 Step 的交付文档。总文档是材料入口，保存 Step 文档和子需求总文档链接；后端 `documents` 有 parentId、stepId、nodeId，身份不依赖可改名的文件名。文本材料导入会成为 SmartDoc 子文档，新生命周期不接受散落的 note/file 作为文档材料。

| 层级 | 归档方式 | 规则 |
| --- | --- | --- |
| 流程总文档 | 流程 handbookId，标题以 00 开头 | 版本目标、范围、Step 文档、需求入口及历史基线 |
| Step 交付 | document.stepId / nodeId | PRD、UI、方案、用例、报告、MR/渠道回执 |
| 子文档/共享材料 | document.parentId 和原生链接 | 在父文档和材料目录中有入口，不建立孤立文档 |
| 已发布输入 | documentId + revision + native digest | 执行固定此修订；草稿不能静默替换 |
| 历史产物 | project / node / Attempt / artifact index / SHA-256 | 产物不可覆盖，总文档经 Step 文档和归档入口定位 |

CI 编辑面板是已有 SmartDoc 引擎上的段落/子文档投影，提供按稳定块 ID 编辑、追加、子文档链接、发布、历史修订和原生下载。没有重新实现完整 SmartDoc 编辑器；表格、公式等完整编辑体验以及与云文档服务的实时在线光标/Presence 同步，本轮未接通，不能宣称已完成云端协同。

## CI Agent 协作者

Agent 使用 `ci_document_get` 读取块与修订，再通过 `ci_agent_document_edit` 贡献内容。记录 `muse-ci-agent` 应用协作者和委托项目成员；人通过 `ci_document_edit` 编辑。两者经过同一项目 ACL、expectedVersion 和 expectedRevision 校验，过期写入失败，不用整篇文本覆盖协作者内容。拥有者可撤回 Agent 的新编辑权限。

这是当前开发 MCP 身份下的应用委托协作者，不冒充独立的云账号或已验证的云端 Presence。生产远端 OAuth/成员身份与原先 Host 平台工作保持独立。

SmartDoc 编辑产生新修订，已发布旧修订和旧 Attempt 保留；受影响的节点及后序 Step 需要重验。人员决定、MR 合并和正式发布授权不由 Agent 的文档编辑获得。

## 新增业务工具

| 工具 | 用途 |
| --- | --- |
| ci_lifecycle_create | 创建版本/独立需求，建立原生总文档和交付目录；可引用历史流程 |
| ci_requirement_create | 事务性创建子需求、父子关系与总文档链接；失败不留下孤儿需求 |
| ci_node_mark | 人工标过及撤回，带原因与审计 |
| ci_document_get/create/edit/publish | 原生文档、子文档、修订与固定输入 |
| ci_agent_document_edit / ci_agent_access | Agent 贡献、委托留痕及权限撤回 |
| ci_repository_bind / ci_mr_verify | 受信仓库/分支绑定及平台 MR 实际回执核对 |

均为插件后端 MCP 业务工具，没有新增 CI 专属 Host RPC。保持命令幂等、项目版本冲突、ACL、材料摘要及不可变历史。
