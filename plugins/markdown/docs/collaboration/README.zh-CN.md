# 思源编辑能力与 AppFlowy 协作融合：可行性与技术选型

> 范围更新：用户已将目标明确为面向 Agent、异构元素同屏、Office 扩展与 Mobile/Web/Desktop 的智能文档平台。最新决议见 [智能文档架构](../smart-document/README.zh-CN.md)。本文件保留前一轮受限编辑器融合评估；其中 AppFlowy Document 作为永久公共模型的建议与 12–18 周排期不适用于新目标，依赖/源码事实仍可参考。

日期：2026-11-04。状态：技术评估与建议，尚未实施或完成运行验证。服务端固定以 `Muse-Server/AppFlowy-Cloud` 为基础；所有周期为本次工程估算。

配套文档：[架构与数据方案](DESIGN.zh-CN.md) · [实施计划与验收](IMPLEMENTATION-PLAN.zh-CN.md) · [代码证据与依赖基线](EVIDENCE.zh-CN.md)。

## 1. 结论与推荐

**可以结合，但必须统一文档模型及事务语义，不能把两个产品直接拼接。推荐主路线为 Flutter 编辑界面 + AppFlowy 文档/协作核心 + 思源能力的分阶段实现；现有 Protyle + Go 插件保留为原生思源格式的兼容入口。**

这符合优先统一 Flutter、兼顾周期与难度的要求，但“Flutter 统一”应理解为正式协作文档的界面与交互统一。复用 AppFlowy 协作仍需 Rust/Yrs；将客户端底层也全部改为 Dart 会丢失成熟协作链路，本评估不推荐。短期兼容思源原生格式仍运行现有 TS/DOM + Go，不把它算作已完成 Flutter 化。

这一推荐有明确前提：首期允许按下文范围交付思源的核心写作/知识管理体验，**不要求第一版无损覆盖完整思源产品**。若第一版必须完整编辑复杂 `.sy/.sydoc`、属性视图、SQL 查询嵌入、原有插件及全部交互，则应改选保留 Protyle 的路线，并接受协作绑定重构与更长验证周期。若必须同时满足全量无损、纯 Flutter、短周期，当前代码基础不能支持这三个目标同时成立。

首期建议将“可协作的 Muse 块文档”和“原生思源文档”作为两种明确的资源能力。已有 `.sydoc` 原样走兼容入口；用户显式转换后产生新协作资源，原文件保留。两种入口不同时写同一文档，不做后台双向自动同步。待 Flutter 能力覆盖达到退出门槛后，再逐步缩小兼容入口。

## 2. 首先纠正“都是 Markdown”的理解

二者都能输入和导出 Markdown，但编辑中的真实文档并非同一种 Markdown 文本：

| 层次 | 思源本地代码 | AppFlowy 本地代码 | 直接融合的问题 |
| --- | --- | --- | --- |
| UI | Protyle，TypeScript、DOM/contenteditable、CSS；Flutter 中由 WebView 承载 | Flutter `appflowy_editor`；另有 React/Slate Web 端 | Protyle 不能编译成 Flutter widget；其选区、输入法、表格逻辑不能直接搬用 |
| 持久内容 | `.sy` 块 AST、IAL 属性、稳定块 ID；附件、AV、历史等旁路数据 | `collab-document`，块表、children、富文本 external text；Yrs CRDT | AST/块类型、inline、引用和附件语义不同 |
| 本地操作 | `update/insert/delete/move` 等事务，`update` 可提交 BlockDOM 后由 Lute 转树 | Flutter 树事务经 `TransactionAdapter` 转块操作与 text delta | 整块 DOM 替换不等于字符级协作操作 |
| 多端 | 本机 HTTP/WS 与思源同步领域 | 本地 Collab 持久化、Cloud WS、状态向量与授权 | 本机 WS 广播不自动具备分布式离线合并语义 |
| 保存 | 当前插件导出 `.sydoc` 包后由资源 SDK CAS 提交 | 协作对象持续增量同步 | 对同一对象再用 ZIP 快照覆盖会抹掉协作合并结果 |

“思源编辑能力”包括三层成本：编辑 UI（块菜单、输入法、复杂表格）、文档语义（引用/嵌入/属性）、内核服务（搜索、图谱、SQL、AV、历史、OCR）。仅替换 UI 既无法带走全部内核能力，也无法解决协作一致性。

## 3. 已有基础与实际缺口

已有思源插件已经完成 Flutter 原生承载、独立资源入口、Go 内核打包、资源导入导出与保存桥。当前 README 明确其本地运行、原厂云同步不启动，资源化设计采用隔离工作笔记本和 `.sydoc` CAS。因此保留原生思源兼容入口的增量成本较低；但不能据此称已有多人协作。

AppFlowy Flutter 端已有编辑事务到文档服务的适配，Rust 端有 `flowy-document`、`collab-integrate`、本地存储插件和 Cloud provider。复用范围应是这些纵向模块，避免把另一套工作区、账户壳、导航与 AI 服务整体带入 Muse。代码抽离仍有 protobuf、dispatch、用户/工作区依赖，不是单独安装 `appflowy_editor` 就可以获得协作。

本地 Cloud 已有 `/ws/v1` 与 `/ws/v2/{workspace_id}` 两种入口、collab 对象存储、权限与同步服务。Web 使用 protobuf 的 v2 消息链；旧实时链使用 bincode。**Cloud 存在 v2，不能把 Web 与 Flutter 的不同封装误判为服务端缺少 Web 协作。** 但必须核验选定客户端、路由、编码和文档版本是否互通。

尤其需要先解决以下基线问题：

1. vendor Flutter 客户端的 Cargo path patch 指向迁移前相对位置；按当前目录解析的 `vendors/vendors/AppFlowy-Collab/collab` 不存在。当前 vendor 不构成可直接复现的独立构建输入。
2. Flutter Cargo.lock 的 Yrs 为 0.21.3；本地 Cloud 为 0.23.5；Web package.json 的 Yjs 为 `14.0.0-1`。版本不同不等于必然不兼容，但无法仅凭共享 CRDT 名称认定兼容。
3. Web、Cloud 有未提交工作区修改；文档中的 HEAD 只标识基线，不代表精确源码快照。需冻结 diff、锁文件和传递依赖后再承诺进度。
4. [官方 AppFlowy-Cloud 仓库](https://github.com/AppFlowy-IO/AppFlowy-Cloud)显示已于 2026-09-11 归档。Muse 应以自己的 fork 维护安全修复和协议兼容，不能假定后续上游持续维护，也不能用商业服务功能宣传推断本地 OSS fork 的能力。

以上是阻止“拿过来即用”的工程缺口，不是否定融合方向。

## 4. 四条路线的取舍

| 路线 | 复用内容 | 主要新增工作 | 优点 | 限制及判断 |
| --- | --- | --- | --- | --- |
| A. Flutter 编辑器 + AppFlowy Collab（推荐） | appflowy_editor、事务/文档服务、Rust/Yrs、Cloud；思源格式作为导入源 | 引用/嵌入/属性等知识能力，格式转换，资源插件化 | 最贴近 Flutter 统一，已有字符级协作操作链，可控制 MVP 范围 | 思源能力需重做；原生全量保真不能短期承诺 |
| B. Flutter 壳 + Protyle + AppFlowy 协作 | 现有 Protyle UI、部分 Lute/Go 服务、Cloud；可参考 Web Yjs 协议层 | Protyle 细粒度双向绑定，改写撤销、选区、输入法、内核投影 | 较高保留思源视觉与编辑习惯；复杂原生文档更易维持 | 两套本地模型最难；保留 UI 不等于保留原样内核；复杂并发下周期不一定更短 |
| C. 继续思源本地编辑 + 云快照/编辑租约 | 现有插件与资源保存 | 上传下载、租约/冲突副本，Cloud 内的附件/资源接口 | 可较快提供跨端保存与串行共享 | 不是同段实时协作，不满足完整融合目标；只能作为有明确产品说明的过渡 |
| D. 将 Protyle、Go 内核及 CRDT 全部重写为 Dart | 主要借鉴行为、格式规范 | 编辑器、解析器、索引、AV、协作协议均需建设 | 语言统一程度最高 | 周期和风险最高，缺少相应收益；不推荐 |

补充：直接采用 AppFlowy Web 编辑器可以复用 Web 协作，但既不统一 Flutter，也不自动获得 Protyle 的能力；只有后续浏览器端是刚需且接受 Web 技术为主要编辑面时才有明显优势。普通 `y-websocket` 不能直接替换 AppFlowy 的消息封装、鉴权、对象初始化与版本语义。

### 4.1 按用户偏好加权

以下 1–5 分为工程判断，5 为更合适，并非跑分；采用首期核心功能范围，不用全量思源保真混入 MVP。

| 维度 / 权重 | A Flutter | B Protyle | C 快照共享 | D 全 Dart 重写 |
| --- | ---: | ---: | ---: | ---: |
| Flutter 界面统一 25% | 5 | 2 | 2 | 5 |
| 首版周期可控 25% | 4 | 2 | 5 | 1 |
| 思源原生保真 20% | 2 | 4 | 5 | 2 |
| 真正实时协作可落地 20% | 4 | 2 | 1 | 1 |
| 长期维护集中 10% | 4 | 2 | 3 | 2 |
| 加权分 | **3.85** | 2.40 | 3.25（不满足实时目标） | 2.30 |

若“原生保真”成为硬门槛，不能再用加权分抵消，应排除 A 的首期方案，选择 B 做验证。B 的优势是已有 UI 和格式服务，主要不确定性是字符级协作绑定，不能声称一定比 A 快。

## 5. 推荐的功能边界

| 能力 | 首期处理 | 后续工作与保真边界 |
| --- | --- | --- |
| 标题、段落、列表、任务、代码、基础表格、图片、链接 | 复用 AppFlowy 已有实现并做实际兼容验证 | Markdown dialect、粘贴与键盘行为需逐项验收 |
| 数学、图表、音视频 | 复用已有 renderer 或增加 Flutter renderer；首期只承诺验收通过的类型 | Mermaid/HTML 等缺少可靠 Flutter 实现时先只读或显式不支持；不能悄悄引入 WebView 后仍宣称全 Flutter |
| 稳定块身份、块引用、反链 | 首期核心新增；跨资源 ID 与权限绑定 | 思源临时内核 ID 不作云文档身份；动态引用文本、重命名跟随分步实现 |
| 嵌入块 | 首期受控只读嵌入 | 嵌入中直接编辑、循环引用、复杂查询嵌入后置 |
| 属性 / IAL | 白名单属性映射；未知字段原始保留 | 保存未知数据不等于可编辑或完整语义兼容 |
| 思源 AV / 数据库 | 原生资源走 Protyle；协作文档仅占位或用户确认后导入受支持子集 | AppFlowy database 不是思源 AV；公式、绑定块、关系、视图需专项映射与并发验证 |
| SQL 嵌入、知识库全局检索、图谱 | 原生模式保留现有能力；协作模式首期仅基础搜索/反链 | 新索引必须带租户/ACL；不能把本地思源 SQL 接口开放为公共云 API |
| 附件/PDF 标注/OCR/闪卡 | 基础附件先行，其余走兼容入口或后置 | 独立对象、权限、历史与转换保真另算 |
| 思源主题/插件/API | 不迁入协作编辑器 | 可用能力通过 Muse 插件接口重新贡献，不能保证二进制/前端 API 兼容 |
| 历史/撤销 | 本地协作撤销 + 云检查点 | 原生思源历史与 CRDT 时间线不同，导入不能自动等价迁移 |

“思源级体验”应使用功能清单验收，不能用相同的斜杠菜单或外观替代语义验收。

## 6. 工期、投入和决策门槛

以 4–5 人有效全职投入为规划基础：2 名 Flutter/编辑器、1 名 Rust/协作、1 名服务端/数据、0.5–1 名跨端测试；熟悉现有 Muse SDK。以下均含首轮集成与回归缓冲，不含新浏览器产品、Windows/Linux 全量认证及完整 AV 兼容。

| 交付目标 | 日历估算 | 工作量区间 | 主要前提 |
| --- | --- | --- | --- |
| G0 依赖冻结及跨版本协作验证 | 2–3 周 | 6–10 人周 | 可获得锁定源码、开发环境；测试 Cloud 隔离部署 |
| A 首期可用协作版（含 G0） | **12–18 周** | 45–70 人周 | 限定上述 MVP；无大规模协议返工 |
| A 扩展知识能力（自项目起） | 5–8 个月 | 80–140 人周 | 引用/嵌入/导入成熟，数据库仅覆盖约定子集 |
| A 追求接近完整思源保真 | 9–15 个月以上 | 160–280+ 人周 | 必须另立范围，不承诺全部第三方插件/主题兼容 |
| B 核心字符级协作版 | 16–26 周 | 60–100 人周 | 2–3 周绑定验证通过；完整 AV/查询协作另算 |
| C 云快照/租约共享 | 4–7 周 | 12–24 人周 | 明确串行编辑，不以此验收实时协作 |
| D 全 Dart 重写 | 12–24 个月以上 | 240–480+ 人周 | 高度不确定，不能作为本期计划 |

人数减半不会简单将日历时间乘二；并发输入、跨端选区、协议和数据迁移具有串行验证成本。G0 失败时应重估而非继续沿用表中排期。计划细分与验收见配套实施文档。

## 7. 许可证与维护边界

本地思源、AppFlowy 完整客户端、AppFlowy Web、Cloud 均含 AGPL 许可文件；不能因为单独 `appflowy_editor` 可选 MPL，就把整个文档/协作核心视为 MPL。本次核查的编辑器固定 ref `470c4e7` 的[许可文件](https://raw.githubusercontent.com/AppFlowy-IO/appflowy-editor/470c4e7/LICENSE)明确列出 AGPL 与 MPL 双许可。实际选用方式、修改文件、链接关系与源码提供义务需按最终依赖逐项落实。

Protyle 放进 WebView 不自动隔离或消除许可证义务；照搬思源代码到 Dart 也不会因更换语言自动改变其许可。发布前交付依赖清单、对应源码、补丁与构建脚本，并复核 Cloud 内自托管协议及第三方包许可适用范围。这里记录工程需要核查的事项，不对整体产品的法律性质作结论。

## 8. 建议确认的技术决议

1. 首期主路径采用 A，统一 Flutter 协作编辑 UI；复用 Rust/Yrs 及现有 Cloud，而非全 Dart 重写。
2. 协作文档以 AppFlowy Document CRDT 为唯一写入源；Markdown 是交换格式，思源 AST 是导入/导出或兼容模式数据。
3. 保留原生思源入口，显式转换，禁止同一资源由两个引擎同时编辑。
4. 用 2–3 周 G0 证明依赖可重现、Flutter/Cloud 双端离线合并、扩展块能完整往返后，再冻结详细版本与交付日期。
5. 若首版全量原生思源保真不可让步，转入 B 的绑定验证；不通过时保留原生单机模式，重新缩减范围，不以整块覆盖冒充协作。
