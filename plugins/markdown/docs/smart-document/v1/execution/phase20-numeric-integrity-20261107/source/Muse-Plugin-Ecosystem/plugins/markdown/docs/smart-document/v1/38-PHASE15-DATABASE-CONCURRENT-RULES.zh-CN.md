# P15：共享视图真正并发提交与稳定规则更新

承接已冻结的 [P14](37-PHASE14-DATABASE-VIEW-RULES.zh-CN.md)：389 份证据，其中 333 份源码/测试输入快照。日期筛选与新增记录预填充继续排入开发队列；先核验 P14 明确开放的真正并发规则提交，避免把依次到达的旧草稿拒绝误认为并发冲突已经解决。

## 问题与复用路径

原 AppFlowy `DatabaseViewUpdate::set_filters/set_sorts` 使用原 `Any::fill(ArrayRef)`，清空数组并创建新的 Map。先通过两个原 Core 分支同时改同一规则、分别改筛选/排序复现，完整交换原更新后检查收敛、规则合法性和保留双方独立改动。

若复现数组重复或互相覆盖，则改为复用原 `ArrayExt::upsert/index_by_id`、原 MapRef 和 Yrs `move_to`，保持现有节点身份，对真正变更的规则执行差量更新，不把未修改的另一类配置重新写一遍。没有新增协作协议、CRDT、后端数据库或文档编辑器内的数据库分支。

## 验收与边界

- 两位作者从同一原状态同时修改同一个已存在的叶规则，双方双向交换/重复交换后必须收敛且不能产生重复规则。
- 一端修改筛选、另一端修改排序，各自独立意图不能因整数组重写而被覆盖；原记录身份与值保持不变。
- 原作者撤销、同伴行编辑和规则重排继续复用原引擎；不能通过重新编码整份状态或增加另一个撤销算法通过测试。
- 真实 Cloud、HTTP 隔离的双客户端、macOS/iOS/Web 配置弹层、跨端读回和重开仍需验收。

结构类型变化、并发新增同 ID、同时移动/删除、复合条件与内容的意图语义必须单独验证。保存一次原事务不等于服务端全局 CAS，遇到未支持的冲突继续保留内容并明确提示，不能宣称完整协作已完成。Android 不安装。

## 已复现与当前实现

两个前置失败均已保留：同时修改已有叶规则、分别改筛选与排序，在原整数组替换后均出现重复规则，双方虽然收敛却进入不支持规则的只读状态。改为原 ArrayExt 稳定 Map 更新与原 move_to；只写实际修改的配置类别，字段/规则身份不重建。已覆盖双向和重复交换、条件/内容配对、空视图独立添加、并发新增不同规则、删除优先与并发排序移动。

还复现原 Yrs 在当前操作已被同伴覆盖时，单次 undo 自动继续弹出更早栈项，导致之前创建的筛选也被移除。Dataset 的跨对象命令时间线需要一次仅消费一个原栈项。固定 Yrs 0.23.5 原发布包，checksum `197c2b4b298f35c3ba4d549884ac872a961112095b29f173ab45e3d5cf609018`，原 Git 3996e91df00acdb67334695944bc43f60627103f；64 个原文件有清单，只修改 undo.rs，增加可选 undo_one_blocking/redo_one_blocking 入口与弹栈数量限制。

原默认公开方法继续使用无限制的原跳过行为；原反演、合并、结构和编解码源码不改。Dataset 显式选用单项入口，正文和协作协议不增加另一套撤销算法。可逆补丁与原文件摘要由 scripts/verify_yrs_vendor.py 核验；原已有代码直接回归，不能仅靠新增方法名宣称兼容。不可撤销的过期项会保留当前协作内容，并在界面说明“这条修改已被协作者覆盖，当前内容已保留”。

目前内容核心 34 项通过，包含原默认 API 与新受限入口的契约、两项并发失败修复、撤销不越界及前期字段/筛选/日期用例。尚待原 Yrs 撤销测试组、真实 Cloud、三端 UI、WASM/Native 往返与新进程恢复，不能标记本轮完成。


## 最终增量验收与职责边界

macOS `20261106T174847Z-concurrent-5ba5d075f568`、iOS `20261106T174956Z-concurrent-1cc3fb214286` 各通过 7 项 UI 与 3 项无凭据新进程恢复。网页沿用 macOS 同一对象，主端 10 项、同伴 8 项、IndexedDB 只读重开 5 项、Native 从原 Cloud 读回 4 项通过。
